# HW-0027: The fast loop runs on SQLite; PostgreSQL authors the migrations and serves

**Status:** Accepted

**Date:** 2026-09-22

## Context

podpack's own seeded `dev.env.example` argues against SQLite by name, and it is
right: "`alembic revision --autogenerate` run against it produces revisions
PostgreSQL may reject — `ALTER COLUMN` is PostgreSQL-only syntax, and a baseline
written that way was fatal on SQLite in this project's own history. Authoring
against the engine you deploy on is the whole point of authoring on the host
(podpack ADR-0011)."

Against that stands what a unit suite is for. Every deployment runs PostgreSQL
in a container; making the fast loop depend on one means a test run needs a
container stack, and CI needs a service.

Both positions are correct about different activities, and the repository had
quietly adopted both without saying so.

## Decision

**Anything that has to be fast runs on SQLite.** `tests/conftest.py` sets
`SQLALCHEMY_DATABASE_URI=sqlite:///:memory:`; CI sets the same, with dummy
secrets, so no service and no real infrastructure is needed; and `README.md`'s
container-free local run points at a SQLite file.

**PostgreSQL is for the container lab, for every deployment, and — without
exception — for authoring a migration.** `dev.env.example`'s argument stands
unamended, because it is about *writing* revisions, not running them.

**The history is written so that both are true**, which is what makes the split
survivable rather than a trap: the baseline's `ALTER COLUMN`s are guarded by an
inspector check and skipped where the columns are already nullable, "and
skipping matters on SQLite, which cannot ALTER COLUMN at all" (HW-0028).

## Consequences

**A test run is seconds and needs nothing installed**, which is what makes the
unit suite something anybody actually runs.

**CI needs no service container**, only dummy environment values — the workflow
says so in a comment rather than leaving the next reader to infer it.

**Nothing enforces the authoring half.** A revision autogenerated against SQLite
would be accepted by the tests, pass CI, and fail on the host. The protection is
a comment in a seeded file that a site is never re-sent (podpack ADR-0026), plus
this record.

**Two engines means two behaviours to keep in mind.** Everything the schema does
must be expressible in both, or guarded as the baseline's alters are. That is a
standing tax on every future revision, and the reason it is paid is that the
alternative is a unit suite nobody runs.

## Alternatives considered

**PostgreSQL everywhere, including tests and CI.** The position
`dev.env.example` argues for, and right for authoring. Rejected for the fast
loop: it makes running the tests an infrastructure exercise, and a suite that is
inconvenient is a suite that is skipped.

**SQLite everywhere, including for authoring revisions.** Rejected, with an
incident behind it: a baseline written that way was fatal, which is exactly what
`dev.env.example` warns about.

**A test double for the database.** Never on the table — the thing most worth
testing here is that the real models map, and a double would test the double.
