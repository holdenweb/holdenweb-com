## On the hosts — Steve's to run

Staging first, production only after staging has been seen working. Until the
role exists *and* somebody holds it, every lablog page answers 404 to everyone,
the administrator included. That is expected, not a fault.

### Staging

0. **On the laptop**, publish main first if you want the deploy to be of
   published code. `deploy.sh` pushes its own `deploy/<target>` ref either way,
   but notes "deploying unpublished code" when HEAD is not on `origin/main`.
   On 2026-11-19 main was ahead of GitHub by `98437de` as well as this change.

1. **On the laptop**, deploy the commit:

   ```bash
   ./ops/deploy.sh staging
   ```

   The rebuild's `migrate` should print
   `Running upgrade 150cf4618ef7 -> d63cab7e83fd, lablog: app schema`.
   `deploy.sh` then polls `/healthz` and fails unless the container reports
   the deployed commit.

2. **On opal17, in `~/apps/hw-stag/site`**, create the role:

   ```bash
   podman compose exec web flask --app holdenweb roles create lablog
   ```

   Expect `Role "lablog" created successfully.` A second run prints the same
   line and then a `UniqueViolation` traceback; the role is there either way.

3. **On opal17, in `~/apps/hw-stag/site`**, grant it to the address you sign
   in to staging with:

   ```bash
   podman compose exec web flask --app holdenweb roles add steve@holdenweb.com lablog
   ```

4. **On the laptop**, check what a stranger gets:

   ```bash
   curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://staging.holdenweb.com/lablog/
   ```

   Expect `302 https://staging.holdenweb.com/login?next=/lablog/`. An
   `http://` there would mean the proxy-hop setting has gone astray, not that
   lablog is wrong.

5. **On the laptop**, run the integration suite against staging:

   ```bash
   uv run pytest tests/integration --base-url https://staging.holdenweb.com
   ```

   Expect 26 passed. It has no lablog tests; it shows the other apps survived.

6. **In a browser**, signed in to staging: `/lablog/` shows the project
   list, and `/_status` reports
   `"reported": {"holders": 1, "role": "lablog", "role_exists": true}`.

### Production

The same steps, with `production` for the deploy target, opal17's
`~/apps/hw-prod/site` for the role commands, and `https://holdenweb.com` for
the checks. `deploy.sh` has no health URL for production (`health_url` returns
blank) and so does not poll `/healthz`. It still asserts the build commit.
Check health by hand:

```bash
curl -s https://holdenweb.com/healthz
```

Expect `"status":"ok"`.
