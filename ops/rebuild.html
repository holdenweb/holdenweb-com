Rebuild: bare host to serving site

Procedure · for whoever is standing at a host with a broken site. Meant to be executed top to bottom, not read for understanding: the reasoning is in ../operations.md. rebuild.sh is the same sequence as a script. Site-specific throughout; nothing here goes to podpack.

Meant to be followed, not read. The reasoning lives in operations.md and this links there rather than repeating it — one place per fact, or they drift, which is how §6 came to say this site lacks a script it has had since 0.7.1.

Every command below is literal. Nothing has a placeholder in it: the values that change between one rebuild and the next are gathered into the configuration block, and every step after that refers to them by name. Fill the block in once, paste it into your shell, and the rest is copy-and-run.

Where a command's output disagrees with what is written, record it and carry on. Do not fix as you go: fixing as you go means only the steps before the first problem are ever exercised, which is how a procedure passes its own rehearsal.

Except where a step says STOP. Three steps make everything after them meaningless if they fail, and carrying on past one produces a page of failures that all say the same thing. They are marked where they arrive: 0.1 (no backup, nothing to restore), Part 3 (no site), and 5.3 (a suite pointed at the wrong host tells you nothing about this one).

  • ☐ — as written; tick and move on.
  • ✎ — write what differed.

The modes diverge in Part 3 and nowhere else that matters. RESTORE is a single command — scripts/restore.sh — because the substrate already ships the whole procedure. FRESH has no dump, so it configures a host and starts it. After Part 3 they rejoin, with one small branch at 5.1 over whether an administrator already exists.

Rehearsal 1's expensive defect was a step that did not branch when it should have — and the reason it existed at all was that this document was hand-rolling what restore.sh already did, in a worse order. If a step below looks like it assumes the other path, that is a bug here; record it.

Timing

Each part opens with a date command. Run it — the timestamps land in your terminal transcript, so timing costs no attention, and the total is the single number a 3am document most needs. There is a table to fill in at the end.

Part 0 — before anything is destroyed

Rehearsal only. In a real emergency the host is already gone; start at Part 1.

runtarget host
date -u +%H:%M:%S

0.1 — Take the backup you will restore from.

The site has to be up for this. backup.sh asks the running web service what to archive, and refuses without it — which is worth knowing before you need it, because in the emergency where the site is down you cannot take a backup. The last good one is whatever you already have. verify-backup.sh needs the stack up too: it reads each dump with the store's own tooling, inside the store's own container.

backup.sh also refuses to write inside the working tree, because the result

holds a verbatim copy of every secret. That guard resolves the destination's parent, so create it first — if the parent does not exist the check cannot run:

runtarget host
mkdir -p ~/backups

Look at what is already there before adding to it, and note which one you intend to restore from — that is BACKUP:

runtarget host
ls -lt ~/backups/holdenweb-com/

A rehearsal that failed after Part 3 leaves a backup here that verifies clean, and it sorts newest. The site it archived was seeded from the packages rather than restored, so it is within a few bytes and one row of the real thing and nothing available tells them apart — verify-backup.sh says VERIFIED for both. Since that command with no argument takes ls | sort | tail -1, the wrong one is what "the latest backup" means until somebody removes it. Delete any such directory now. Backlog #22 is fixed in podpack 0.9.0b4 — verify-backup.sh now names any table whose count has fallen since the previous backup, and prints the source directory: that every manifest has recorded all along. This step stays: it fires before the restore, on the backup you are about to trust, and whether a directory should be deleted is a judgement only you can make.

runtarget host
./scripts/backup.sh
runtarget host
./scripts/verify-backup.sh

Expect: a directory under ~/backups/<site>/, mode 0700, holding

manifest.txt, plan.json, database.pgc, app-data.tar.gz,

config.tar.gz, rowcounts.txt, env — no leading dot — and secrets.env.

verify-backup.sh ends VERIFIED: and names the git commit and alembic

revision.

0.2 — Record the host as it is, so the rebuild can be compared to it.

runtarget host
python3 scripts/configure-host.py --check
runtarget host
podman compose ps

Expect: --check writes nothing, and reports which values are still the example's plus whether this host can run containers — the Compose v2 provider, the podman socket, and lingering. It needs .env and secrets.env to exist already; on a bare clone it says not configured yet and stops.

A backup that fails part way leaves nothing behind: backup.sh removes the destination if the plan names no store, if a dump comes out empty, or if a store named in the plan produced no file. So a directory that exists is a directory that got to the end.

0.3 — Wipe it, which is the step that makes this a rehearsal rather than a reading. Only after 0.1 has produced a backup you have verified.

runtarget host
podman compose down

down removes the containers and the network. It does not remove

hostdata, and that is the distinction worth keeping straight: hostdata is

the database and the site's content.

Then remove the checkout entirely — data, logs and clone together — from its parent directory, which is also where Part 2 wants you:

runtarget host
cd .. && podman unshare rm -rf "$SITE_DIR"

rm -rf without podman unshare will fail, and not because of a permissions mistake. prepare-host-dirs.sh ran podman unshare chown to hand hostdata and hostlogs to the containers' unprivileged uids — 10001 for the app, 999 for postgres. Under rootless podman those live inside your user namespace and surface on the host as subuids from your /etc/subuid range, so ls -l shows an owner you do not recognise and you cannot delete them. podman unshare re-enters that namespace, where they are yours again. podman unshare ls -la "$SITE_DIR/hostdata/apps" to look first. And mind where you are standing. rm -rf on a path that does not exist succeeds silently, so running this from the wrong directory removes nothing and says nothing — after which the failing rm looks like the unshare did not work. Observed in rehearsal 3.

Part 2 — clone

runtarget host
date -u +%H:%M:%S
runtarget host
git clone "$SITE_REPO" "$SITE_DIR"
runtarget host
cd "$SITE_DIR"

Expect: config/, src/ and alembic/ present — those are in git, and git is their backup. No .env, no secrets.env, no hostdata/.

Know which checkout you are in. Two checkouts of one site coexist perfectly well provided two things differ: SITE_NAME after compose normalises it — dots are stripped, dashes kept, so holdenweb.com becomes holdenwebcom while holdenweb-com stays as it is — and WEB_HOST_PORT, which is the only genuine bind clash. Images do not collide: measured. What does go wrong is a person forgetting which directory they are in, which is most of what went wrong in rehearsal 1.

Part 3 — BRANCHES: bring the site into existence

runtarget host
date -u +%H:%M:%S

This is where the two modes stop resembling each other. Follow one heading and skip the other entirely.

MODE=RESTORE — one command · STOP IF THIS FAILS

Check the backup is the one you mean, and complete — restore.sh refuses on a missing file, but reading the names first is cheaper than reading its refusal:

runtarget host
ls -l "${BACKUP:?}"
runtarget host
./scripts/restore.sh "$BACKUP"

If it exits non-zero, stop here and read what it said. This checkout is a fresh clone, so it has no .env of its own and restore.sh installs the backup's — including its SITE_NAME, which is the compose project every later command will act on. Both files go in before anything is unpacked, so a failure after that point leaves this directory carrying the backup's identity, and continuing means operating on the backup's deployment from here. Backlog #19 is struck as of podpack 0.9.0b4 and this warning still stands: the fix keeps an .env that already exists, and a fresh clone has none.

That is the whole of it, and it is worth knowing what it is doing rather than treating it as magic, because it stops twice to ask you things:

1. Is this the right backup and the right target? It prints what it is restoring from and into, and waits for you to type restore. 2. Does the code match the data? It compares the backup's commit against this checkout and says which way you are rolling — a newer checkout means alembic rolls the data forward, which is fine; an older one may not know about tables in the dump.

Then, in an order chosen to avoid the two traps that a hand-run restore falls into: it puts secrets.env back, keeping yours as .superseded-<stamp>, and either keeps your .env or — as here, in a fresh clone — installs the backup's and names every per-host value in it; unpacks the app data before the first

compose up,

because init-storage hands the mounts to the containers' uids and does not run twice; removes each restored app's directory first, because tar only ever adds and a merge is a state that never existed; brings each store up alone, so its bootstrap creates the role the dump's objects belong to; then the rest of the stack, which makes migrate a free consistency check.

Finally it verifies out loud — every table's row count against

rowcounts.txt, and /healthz — and exits non-zero if either fails.

On a host whose port differs from the old one, expect it to fail at the last step, and expect that. This is a fresh clone, so .env comes from the backup carrying the old WEB_HOST_PORT, and the health check polls a port nothing is listening on. (Restoring into a checkout that already has an .env keeps it, and this does not arise.) The data is restored correctly; only the last check is wrong. Fix it: ``bash sed -i "s/^WEB_HOST_PORT=.*/WEB_HOST_PORT=$WEB_PORT/" .env ` `bash ./scripts/up.sh ` Check the other per-host values in .env while you are there — WEB_BIND_ADDR, and VOLUME_RW/VOLUME_RO if this host's SELinux differs from the old one's. python3 scripts/configure-host.py --check` reports them without writing anything.

Do not run configure-host.py --port on this path. It would generate a

.env and secrets.env that restore.sh then replaces with the backup's, and

fresh secrets are the one thing a restore must not have.

MODE=FRESH — no dump, so no restore.sh

runtarget host
python3 scripts/configure-host.py --port "$WEB_PORT" --site-name "${PROJECT:?}" --data-dir ../data --log-dir ../logs

Expect: wrote .env and secrets.env (0600) for '<PROJECT>', then the port, a database and role named after PROJECT, whether SELinux is enforcing, and that secrets were generated with none printed. It refuses to overwrite either file, so a second run is safe.

Every flag is there because its default is wrong on a real host. Without

--site-name the project, database and role are named after this directory —

site, in a deploy target's ~/apps/<app>/site. Without --data-dir and

--log-dir the data goes in ./hostdata, inside the checkout, where a fresh

clone or a git clean takes it with them; prepare-host-dirs.sh refuses that outright once the next step makes this a real deployment. ../data resolves against the checkout, so data and logs sit beside it in the app's directory, which is how staging is laid out (DEPLOY.md).

configure-host.py has no option for the environment. It leaves the example's

local, and even lists it among the values "usually fine" — which it is in a

lab, and nowhere else. Set it:

runtarget host
sed -i "s/^PODPACK_ENVIRONMENT=.*/PODPACK_ENVIRONMENT=${ENVIRONMENT:?}/" .env
runtarget host
grep -E '^(SITE_NAME|HOST_DATA_DIR|HOST_LOG_DIR|WEB_HOST_PORT|PODPACK_ENVIRONMENT)=' .env

Expect: SITE_NAME is PROJECT, the directories are ../data and

../logs, the port is WEB_PORT, and PODPACK_ENVIRONMENT is ENVIRONMENT.

Left at local, the site trusts no proxy and every password-reset link goes out http:// (Part 4), and prepare-host-dirs.sh would accept data inside the checkout without a word.

Watch for: the SELinux line. not enforcing leaves VOLUME_RW/VOLUME_RO empty and is right on a permissive host; detected sets them to :Z/,z. A host can be labelled but permissive, which is what Opalstack is today — if it is ever switched to enforcing, this decision changes and the mounts break.

It also names any value still at the example's, which on this path will include

MAIL_PASSWORD. Set it now, in secrets.env: sixteen letters, spaces removed,

and no $, which compose expands there as well as in .env.

runtarget host
./scripts/prepare-host-dirs.sh

Expect: ready: lines under ../data and ../logs, none under the checkout.

runtarget host
./scripts/up.sh

Expect: postgres healthy, migrate exited cleanly, web started.

Part 4 — confirm the site believes its proxy

runtarget host
date -u +%H:%M:%S

This used to be a step that set something, headed "the setting nothing will tell you about". It is now a step that checks one, because podpack derives the trusted-hop count from PODPACK_ENVIRONMENT (ADR-0039). That variable is in this host's .env already, restore.sh brings it back with the other per-host keys, and a value of anything but local means one nginx is trusted. Nothing to add.

Ask the site what it concluded, rather than what it was told:

runtarget host
podman compose exec web python -c 'from podpack.proxy import proxy_hops; print(proxy_hops())'

Expect: 1. This reads the effective count however it was arrived at, so it answers on the podpack that derives it and on any older one that does not — which is the point of asking this way rather than reading the variable.

If it says 0, the site will build every _external=True URL as

http://, and the first thing to carry one is a password-reset mail with a

token in the path. Two causes, fixed differently:

  • This host runs a podpack predating ADR-0039, so nothing derives the count. ops/rebuild.sh repairs this itself: seeing a zero on a non-local host that declared nothing, it appends PODPACK_PROXY_HOPS=1, recreates web and asks again, printing a line when it does. Doing it by hand is the same two steps — no export prefix, compose's env_file is not a shell and would read the name as export PODPACK_PROXY_HOPS — then ./scripts/up.sh.
  • PODPACK_ENVIRONMENT says local on a host that is not a lab. Nothing repairs this, deliberately: the variable is wrong for prepare-host-dirs.sh too, and guessing which of the two is the mistake would be the wrong kind of help. Correct it in .env.

The repair leaves a declared count alone in every case. PODPACK_PROXY_HOPS=0 on a non-local host is the documented way to say nothing is in front of you, and overwriting it would hand a directly reachable site a forgeable

X-Forwarded-Proto.

Note: the count is the number of values in X-Forwarded-Proto, not the number of proxies. One nginx that overwrites the header is 1 however many boxes sit behind it. A host behind two proxies, or a non-local host behind none, still says so with PODPACK_PROXY_HOPS, which always wins.

5.1 — BRANCHES

MODE=RESTORE — nothing to do. Your accounts came back with secrets.env; sign in as yourself.

MODE=FRESH — make an administrator, or /_status answers nobody:

fill intarget host
runtarget host
podman compose exec web flask --app holdenweb users create "${ADMIN_EMAIL:?}" --active
runtarget host
podman compose exec web flask --app holdenweb roles create admin
runtarget host
podman compose exec web flask --app holdenweb roles add "$ADMIN_EMAIL" admin

The first stops and asks for a password. The address must be able to receive mail: flask-security checks deliverability, so you@example.com is refused — that domain publishes no MX record.

**5.5 — Prove the backup regime on this host.**

runtarget host
./scripts/backup.sh && ./scripts/verify-backup.sh

Only meaningful if no STOP step failed. If one did, the site this just archived is not the restored site, and the archive is now the newest in a directory people reach into for "the latest". verify-backup.sh will call it VERIFIED regardless, because it is a valid backup — of the wrong thing. Delete it before you walk away.
